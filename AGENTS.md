# LexiFin

Currently only SEC 10-K/10-Q/8-K filings of the top-N companies in the IVV ETF (S&P 500). Never break the immutability of Bronze and `filing_manifest.jsonl`: the manifest decides which filings are downloaded again.

## Commands

- Install: `uv sync --locked` (Python 3.13; `vnstock`/`vnai` come from the private index `vnstocks.com`).
- All tests: `uv run pytest` (~470 tests, ~8 min, no network; coverage is on in `addopts`). `make check` runs every CI step (`.github/workflows/ci.yml`: ruff format + lint, mypy strict, vulture with `vulture_whitelist.py`, jscpd, pytest; ~9 min); config lives in `pyproject.toml`. Most of the time is Arelle loading fixture taxonomies: each pipeline run in the integration tests has three XBRL stages that load instances (facts, enrichment, linkbases; ~0.25 s per load), then the integrity gate audits everything again.
- One test: `uv run pytest tests/unit/utils/test_timer.py::<test_name> --no-cov`.
- SEC ingest (Bronze):
  `uv run python scripts/ingest_sec_edgar.py --data-dir <tmp_dir> --company-limit 1 --lookback-years 1`
  Needs `SEC_COMPANY_NAME`, `SEC_EMAIL` in `.env` (template: `.env.example`). Without `--data-dir` it writes to `./data`.
- Build Silver (Iceberg) from all SEC Bronze, offline:
  `uv run python scripts/sec_filings/build_silver.py --data-dir <data_dir> [--from-stage S] [--to-stage S]`
  Stage order: `filings` → `documents` (one row per `<DOCUMENT>` block of `full-submission.txt`) → `filing_entities` (one row per entity-role block such as `FILER:` in the SEC header) → narrative (`sections` + `content_blocks`, from one parse of each narrative document: the primary HTML and every EX-99 HTML exhibit, `is_narrative_document` in `storage/sec_filings/documents.py`; an exhibit is one root section, an exhibit without visible text such as an image-only slide deck gets no rows and is parsed again every run) → tables (`document_tables` + `document_table_cells`, one table per `table` block) → links (`document_links`, one row per `<a href>` of every HTML document) → exhibit index (`exhibits`, one row per Exhibit Index entry of the primary document; reads stored sections, `table` blocks, cells and links) → XBRL core (`xbrl_instances` + `xbrl_contexts` + `xbrl_units`, one parse per Inline XBRL/XML source; depends only on filings and documents) → XBRL facts (`xbrl_concepts` + `xbrl_facts`, each instance loaded with its DTS by Arelle; taxonomies from `<data_dir>/_cache/arelle`, override with `--taxonomy-cache-dir`) → XBRL enrichment (`xbrl_dimensions` + `xbrl_fact_footnotes`, same loader) → XBRL linkbases (`xbrl_labels` + `xbrl_networks` + `xbrl_relationships`, from each instance's DTS) → integrity (read-only audit of all 19 tables, below). All tables are in namespace `sec_filings`. Later stages read parents from Silver, not Bronze. Stage order, dependencies and tables are declared once: `SILVER_STAGES` in `pipelines/sec_filings/silver_stages.py`; `bronze_to_silver.py` runs a stage range and summarizes the run; each stage lives in `pipelines/sec_filings/<stage>.py`. Grain, keys, relations, lineage and deliberate denormalization: `docs/data/sec_filings_silver_model.md`.
  `--data-dir` is the Silver root (`_catalog/`, `silver/`, `_cache/arelle`). Bronze defaults to `<data_dir>/bronze/sec_filings`; override with `--bronze-dir <dir holding sec-edgar-filings/ and _metadata/>` (also on `audit_silver.py`) to keep Bronze and Silver apart, e.g. `--bronze-dir /media/bee/DATA/02_projects/LexiFin/data/bronze/sec_filings_10 --data-dir /media/bee/DATA/02_projects/LexiFin/data/silver/sec_filings_10`. Bronze paths stored in Silver keep the manifest form `bronze/sec_filings/...` and resolve under `--bronze-dir` (`SecBronze` in `storage/bronze.py`), so Bronze can move or be renamed without a rebuild; the audit must use the same `--bronze-dir`.
  `--list-stages` prints stage order, dependencies and tables, then exits. `--from-stage` skips earlier stages: every table it depends on must already exist with the right contract, otherwise no stage runs (exit 1). `--to-stage` stops after that stage; `integrity` runs only when the range reaches the end. Each run has a `run_id`; `silver_pipeline_*`/`silver_stage_*` logs carry `pipeline`, `run_id`, `data_dir`, `stage`, and the final summary (also printed) has completed/skipped stages, `failed_stage` (+ its counters), rows added per table (from snapshot metadata), new tables, changed snapshots and the integrity result.
  On the first run (or when a filing uses an uncached taxonomy) add `--allow-taxonomy-network` so Arelle downloads standard taxonomies (us-gaap, dei, srt…) into the cache. Default is offline; a missing file rejects the XBRL facts stage and logs `xbrl_taxonomy_cache_miss` with the URI.
  `--xbrl-workers N` (default 1): the three XBRL stages load instances with Arelle in N `spawn` processes (`load_ahead` in `pipelines/sec_filings/xbrl_instance_loading.py`, reading at most 2N instances ahead; the pool is recreated per batch). The main process still builds rows in instance order, so data does not depend on N; an instance's error (including `TaxonomyUnavailable` in a worker) stays attached to that instance. On `data/` (2026-10-20, offline): N=3 gives the same fingerprint of all 19 tables as N=1, XBRL stages 2,270 s → 1,024 s, whole build 42.7 → 22.3 min, process-tree RAM ~3.7 GB (N=1: ~2.3 GB). Each worker adds ~1 GB; the main process mostly waits (CPU/wall ≈ N), so larger N is faster given RAM.
  Builds through `run_sec_filings_silver` cache each instance's load result (pickle + zstd, ~7–400 KB per instance, ≤ 0.2 s to decompress vs 0.3–3.5 s for Arelle) in `<data_dir>/_cache/xbrl_instances` (`InstanceCache`, `ProcessorSettings.instance_cache_dir`): only the first XBRL stage that needs an instance runs Arelle, the next two read the cache, even in another process or after an interrupted build. The key is `source_set_sha256`, target and loader version (Arelle version + source hash of `xbrl_instance_loading` and every repo module it imports, directly or not: `code_sha256` in `src/data_pipeline/code_version.py`, which reads static imports with AST, so edits outside that closure keep the cache). Entries carry a zstd checksum, so a damaged entry (read error or wrong bytes) is always a miss and the instance is reloaded, never wrong rows. A failed write (full disk…) only logs `xbrl_instance_cache_write_failed` and the build continues. The directory is deleted after linkbases. Source files are still read and verified in every stage. Calling a stage directly (tests) has no cache.
  Full build of 343 filings (offline, warm taxonomy cache; 2026-10-07): ~41 min, peak RSS ~2.6 GB. Per stage: filings 8 s; documents 11 s; filing_entities 1 s; narrative 37 s → 2,803 sections, 83,301 blocks; tables 98 s → 10,184 tables, 878,380 cells (EX-99 narrative added 2026-11-03 in one incremental run: narrative 9 s → +179 sections, +14,131 blocks, 1 image-only exhibit without text; tables 30 s → +1,776 tables, +273,829 cells; every earlier row unchanged); links 31 s → 365,221 links; exhibit index 1 s → 2,696 entries; XBRL core 19 s → 343 instances, 30,319 contexts, 699 units; XBRL facts ~12.6 min → 140,764 concepts, 133,384 facts (online with an empty cache is much slower, ~7 s per instance); XBRL enrichment ~10.7 min → 43,405 dimensions, 775 fact-footnote relations; XBRL linkbases ~12.7 min → 157,825 labels, 14,918 networks, 338,171 relationships; integrity ~80 s.
  Memory does not grow with table size: each stage classifies parents from group summaries of stored tables (count, ordinals 1..N, declared count, parent lineage; a few columns read in batches, see `summarize_groups`/`scan_batches` in `storage/iceberg.py`) without rereading rows, then builds, validates and commits in batches (`DOCUMENTS_PER_COMMIT`, `FILINGS_PER_COMMIT`, `INSTANCES_PER_COMMIT` per stage; tables also closes a batch before `TABLE_BLOCKS_PER_COMMIT` `table` blocks, because RAM follows cell count, ~5 KB/cell, and batches sorted by `filing_date` would otherwise pack ~1M cells of a 10-K/10-Q season into one batch). Each batch reads only its parents' rows (partition filter on `filing_date`), and the post-write check reads only the files that append added. Stages do not recheck full stored groups (whole-section/table/network hashes…): the integrity gate checks every row and every count/key, and full-group hashes on sampled filings.
  Rerun: ~1.5 min, peak RSS ~0.75 GB (integrity ~75 s; other stages 2–5 s, ≤ 0.4 GB). Every existing group is skipped; links reparses documents with no links (no row marks them done); exhibit index rebuilds every entry from Silver per filing batch and compares; XBRL core skips complete filings without reading Bronze (filings without XBRL are reparsed); XBRL facts/enrichment/linkbases skip complete instances without Arelle; enrichment reads the source document of instances with no footnote rows to confirm they have no footnote markup.
  Exit 1 when a table the run reads or writes differs from its definition (see rules version below), when a stage rejects (bad filing, checksum conflict, missing or different document/entity/narrative/table/link/exhibit/fact group, missing taxonomy, Arelle disagrees with XBRL core), when integrity finds an error, or when a prerequisite is missing. Conflicts found while classifying reject the stage before its first write; an error inside a batch writes nothing for that batch and stops the stage, earlier batches stay committed (skipped next run); later stages do not run (fail-fast, no global rollback). Exit 2 on bad arguments (unknown stage, `--from-stage` after `--to-stage`, `--check-only` with a stage range). Narrative writes sections before blocks, tables writes document_tables before cells, XBRL core writes instances → contexts → units, XBRL facts writes concepts → facts, enrichment writes dimensions → footnotes (siblings: a missing table is backfilled alone next run), linkbases writes labels → networks → relationships: if a later commit fails, the next run resumes when the stored part matches exactly.
- Silver audit, read-only and memory-bounded (one implementation: `quality/sec_filings/silver_audit*.py`, tables/keys/FKs in `silver_model.py`); it is the final `integrity` stage of the build and also runs alone:
  `uv run python scripts/sec_filings/build_silver.py --data-dir <data_dir> --check-only`
  `uv run python scripts/sec_filings/audit_silver.py --data-dir <data_dir> [--sample-per-form 1] [--batch-size 10000] [--verify-source-hashes] [--work-dir D] [--workers N]`
  Opens the SQLite catalog read-only and validates every row against its contract, one task per Parquet data file (`--workers N` `spawn` processes; build: `--audit-workers`, `run_silver.sh`: `AUDIT_WORKERS`, default 4; results merge in file order, so the report does not depend on N). DuckDB then reads key/lineage/group columns straight from those files into a scratch DuckDB database (`audit.duckdb` under `TMPDIR`, auto-deleted; capped at 4 GB RAM, overflow spills to `audit.duckdb.tmp`; hash joins, no indexes) to check duplicates, 32 FKs + lineage, groups 1..N and declared counts, the section tree, `table` block semantics, cell grids, XBRL sources and relationship attributes. It also checks that every filing's Bronze files exist (`--verify-source-hashes` rehashes all).
  `--work-dir D` (build: `--audit-work-dir`; `run_silver.sh` uses `<out>/tmp/audit`) keeps the scratch database at `D/audit.duckdb` (DuckDB replays the WAL on reopen) with the completed steps (each scanned table, each SQL check). An interrupted audit (crash, power loss) replays those steps and continues, provided table snapshots/row counts, `--sample-per-form` and the audit code (`code_sha256` of `silver_audit`, including every module it imports) are unchanged; otherwise the files are deleted and the audit restarts. The Bronze check and sampled filings always rerun; a finished audit (even with FAIL) deletes the files. On 500-company Bronze with the old SQLite scratch (2026-10-25): scan 3.4 h, indexes + SQL checks 14.5 h, whole audit 18.4 h, ~145 GB scratch. On 10-company Silver (735 filings) DuckDB matches SQLite (266 checks, same status/counts), SQL checks 21.3 → 2.4 s; a check's sample IDs are the first rows DuckDB returns, order not fixed.
  Then, for the latest 10-K/10-Q/8-K filing, it goes back to Bronze: rehashes the submission, rebuilds documents/entities/sections/blocks/tables/cells with the stage code and compares with Silver, recomputes the hashes that need a whole group's text (`section_text_sha256`, `table_content_sha256`, `network_hash`; samples only), and prints the section outline and a few facts. Finally it compares table metadata and catalog/warehouse file stats before/after. The report has PASS/WARN/FAIL/SKIP per check (up to 5 sample IDs); logs `silver_integrity_*`. Exit 0 = no FAIL, 1 = FAIL, 2 = could not run (missing catalog…). On `data/` (2026-10-07, SQLite scratch): ~80 s, peak RSS ~0.7 GB, ~1.1 GB scratch on disk (linear in rows); 263 PASS, 2 WARN (149 `public_document_count`, 1,154 unresolved links), 0 FAIL, 1 SKIP (`source_hashes`).
- Silver benchmark (time, CPU, RAM, throughput, scaling, rerun); writes `report.md`, per-process logs and `rss_samples.csv` to `--work-dir` (new/empty); reads `--bronze-dir` only; Linux:
  `uv run python scripts/sec_filings/benchmark_silver.py --bronze-dir <bronze> --work-dir <new_dir> --taxonomy-cache-dir <cache> [--fractions 0.25 0.5 1] [--xbrl-workers N] [--project-filings N] [--skip-incremental]`
  Large Bronze: `scripts/sec_filings/run_silver.sh {all|warm|bench|build|status} <bronze> <out>`. `all` = warm → bench → build → status. warm = `warm_taxonomy.py` scans schema URLs in a 2% Bronze sample (~2.5 min on an exFAT drive at ~34 MB/s) and downloads missing taxonomies into the cache. warm/bench are skipped when `bench/taxonomy.json`/`report.md` exist, so rerunning `all` resumes. build runs offline; when a stage rejects with `xbrl_taxonomy_cache_miss`, the logged URIs are downloaded and the build reruns, up to `TAXONOMY_RETRIES` times. Everything goes under `<out>` (Silver, `_cache/arelle`, `logs/`, `tmp/` = `TMPDIR`, `bench/`); each step has a hard RAM cap `MEMORY_MAX` (default 12G) and `WORKERS` (default 3); `build` appends to its log, so rerunning the same command resumes; extra arguments go to `build_silver.py`.
  Each stage runs in its own `build_silver.py --from-stage S --to-stage S` process (measured with `wait4` + `/proc` sampling of the whole process tree), so RAM is per stage. Scenarios: full build per Bronze sample (nested samples by `filing_id` hash; files are hard links, or copies across file systems or on drives without hard links such as exFAT), then `rerun` (nothing new) and `delta` (Silver of a smaller sample updated to the largest). A stage's `TMPDIR` is `<work-dir>/tmp` (`--tmp-dir`), where integrity writes its scratch DuckDB. RAM is not extrapolated: stages commit in batches, so peak is the heaviest batch (on small samples RAM still grows because batches are not full); the "RAM first / second half" column only shows whether RAM climbs with data when a stage runs many batches, so RAM scaling needs samples large enough for every stage to have many batches. On `data/` (2026-10-20, N=1), multi-batch stages do not climb (peak first / second half, MiB: xbrl_facts 2,099 / 1,958, xbrl_linkbases 1,106 / 1,047, xbrl_enrichment 665 / 642, document_tables 1,852 / 1,877, document_links 560 / 589); single-batch stages are inconclusive. ~95% of XBRL time is Arelle loading the DTS; rerun 107 s (integrity 75 s); delta 50% → 100% (182 filings) 23 min.

## Domain terms

Easily misread names:

- universe: top-N by total IVV `Weight (%)`, grouped by CIK (GOOGL + GOOG count as one company). Not the official S&P 500 list.
- `company_limit` (N, 1–500): incremental state is split by N. `load_usable_runs` reads only runs with the same N, so changing N marks every company `new` and rescans all `lookback_years`. Filings already in the manifest are skipped but SEC is still called to list them.
- `snapshot_id`: SHA-256 of the two source files, not a date. Folder `snapshot_date_<ts>` is the run start time (UTC), not `holdings_as_of_date`.
- `cik`: 10-digit string with leading zeros (`0000320193`), not an int.
- `status="partial"`: some filings failed, but the script still exits 0. `exited` is written only in the run right after a company leaves the universe.
- `connectors/sec_filings/` also holds `ishares.py`, though iShares is not an SEC source.
- The `integration` marker does not mean network; those tests use fake fetchers/downloaders. Tests in `tests/unit/utils/` have no marker, so `-m unit` misses them.
- Silver is Iceberg (PyIceberg + DuckDB, not Delta). Unpartitioned: `filing_entities`, the three XBRL core tables, `xbrl_concepts`, `xbrl_dimensions`, `xbrl_fact_footnotes`, `xbrl_labels`, `xbrl_networks`, `xbrl_relationships`. `xbrl_facts` is partitioned by `bucket(32, instance_id)` (field `instance_bucket`); the rest by `year(filing_date)`. Gold has no code yet.
- Each `<table>` with at least one visible cell is exactly one `block_type="table"` content block (`source_tag="table"`, text = non-empty cells joined by `\n`, may be empty); cells are not content blocks. A nested table with cells is its own block; one without cells belongs to the outer cell's text. A heading inside a table makes the whole `table` block a heading; a section `title` is normalized text (cells joined by spaces, no `\n`). If `content_blocks` still has `table_cell` rows of the old layout, narrative logs `narrative_table_semantics_incompatible`, rejects (exit 1) and writes nothing until a controlled rebuild of `sections` + `content_blocks` (done for `data/` on 2026-10-06).
- SEC tables in Bronze never use `<th>`, `<caption>` or `thead`/`tfoot` (all cells `td`, row group `body`); ~69% of cells are empty padding; `colspan > 1` is common. Hidden cells (44,472 `<td style="display:none">`, all empty, in 93 filings) are not rendered and not stored: `cell_count`/`row_count` count visible cells/rows only, so they differ from raw `<td>` counts.
- `content_blocks.source_xpath` is `getpath()` of the HTML-mode DOM, so Inline XBRL segments keep prefixed tag names (`/html/body/ix:nonnumeric[1]/p[1]`, ~44% of blocks). Standard XPath treats `ix:` as a namespace prefix: to evaluate, write that step as `*[name()='ix:nonnumeric'][1]`.
- Rules version: each table's `SilverTableSpec.rules_version` (default 1) is the version of the rules that build its rows from Bronze, stored as table property `lexifin.rules-version` at creation (tables created before it carry none and count as 1). Stages skip existing groups by source hash, so they cannot see a rule change themselves. A run whose tables (written, or read as prerequisites) differ from their definition (schema, partitioning, rules version) runs no stage: `table_problems`, log `silver_tables_invalid`, exit 1; the audit's `table_definition` check fails. `test_rows_change_only_with_the_rules_version` pins each table's rows digest on the fixture Bronze with its rules version: when a code change builds rows of an already built group differently, bump `rules_version` of every table whose digest changed (downstream tables built from changed IDs change too) and record the new digests. A change that only adds groups for parents not covered before (old fixture rows a subset of the new ones, e.g. EX-99 narrative, 2026-11-03) keeps the version: record the digests, and the next run adds those groups like a new filing's. Controlled rebuild: purge the bumped tables, plus any table written by the same stage, then build:
  ```bash
  uv run python - <<'EOF'
  from pathlib import Path
  from src.data_pipeline.storage.iceberg import open_silver_catalog
  with open_silver_catalog(Path("<data_dir>")) as catalog:
      for table in ("sec_filings.sections", "sec_filings.content_blocks"):
          catalog.purge_table(table)
  EOF
  ```
- `document_links`: `source_document_id` and `target_document_id` both reference `documents.document_id` (an exhibit is a document; there is no `target_exhibit_id`). Targets resolve only within the same filing by exact filename; an SEC URL under another filing's accession folder is always `unresolved` even when the filename matches. In `data/`: ~97% of rows are `javascript:void(0)` from SEC-generated R pages (`role=generated`, `not_applicable`); 861 exhibit HTMLs have no links; the 1,154 SEC URLs all point to older filings (referenced exhibits), so `unresolved`; no external URLs.
- Section hierarchy lives only in `sections.parent_section_id` (no child-sections table): PART is a child of root; a 10-K/10-Q ITEM is a child of the open PART (level 2), or of root without a PART; SIGNATURES, EXHIBIT INDEX and TABLE OF CONTENTS are children of root and close the open PART. 8-Ks have no PART, so every item is a child of root. Level always rises by exactly 1, so cycles are impossible.
- `exhibits` has a different grain from `documents`: an attached exhibit is a `documents` row with `role="exhibit"` (861 in `data/`); `exhibits` is a filing's declared Exhibit Index line. An entry may point to an exhibit in this filing (`resolved_document_id`, from a resolved `document_links` link), to an older filing (incorporated by reference: SEC URL in `href`, unresolved), or have no link. Search area: section `exhibit_index`, 10-K ITEM 15, 10-Q PART II ITEM 6, 8-K ITEM 9.01. A table qualifies when it has a header row with an exhibit-number column and a description column (rows without a number count as `rejected_rows`), or when it has no header but has entries and every other non-empty row is an entry (number + description) or a one-cell note (8-K Item 9.01 and continued tables). `exhibit_number` drops footnote marks (`10.1*` → `10.1`); a row with inconsistent links gets a null `href` (warning `exhibit_entry_links_conflict`, 4 entries). In `data/`: 861/861 attached exhibits have an entry pointing to them, 1,074 entries point to older filings, 15 Power of Attorney entries resolve to the primary document itself (anchor to the signature page). Every run rebuilds all entries and compares with the table, so a parse-rule change makes filings with different entries conflict (exit 1): bump its rules version and rebuild `exhibits` under control (done 2026-10-07, before rules versions).
- XBRL core: EDGAR wraps iXBRL `.htm` in `<XBRL>` and `.xml` in `<XML>`; that SGML wrapper is stripped before XML parsing (namespace-aware, no DTD/entities/network). Every filing in `data/` has exactly 1 default Inline target (no named targets, no `ix:tuple`) + 1 EDGAR-generated XML (`TYPE=XML`, `*_htm.xml`); the XML merges into the target (`source_document_ids` lists both) when schema refs, the (concept, contextRef, unitRef) multiset and all its contexts/units match. EDGAR's XML drops units no fact uses, so Inline can have more units. `namespace_map` comes only from the canonical (Inline) source, since the XML's `""` prefix is `xbrli`. `segment_xml`/`scenario_xml` are self-defined canonical XML (prefixes `ns0…` by URI, QNames in `dimension`/`explicitMember` rewritten, inter-element whitespace dropped, members sorted by dimension, then C14N) so both representations give the same `context_hash`. The three tables are unpartitioned and child tables do not repeat `filing_id`/`filing_date`.
- XBRL facts: Arelle (`arelle-release`, wrapped in `transforms/sec_filings/xbrl_processor.py` + `xbrl_model_reader.py`) reloads each instance with its DTS from verified documents; fact count, context refs and unit refs must match XBRL core, otherwise it logs `xbrl_core_semantics_incompatible` and rejects. `xbrl_concepts` is a global dictionary keyed by expanded QName (`concept_id` = sha256 of `namespace\x00local`), covering the whole DTS (18–22k concepts per filing, including dimensions/members/typed domains; each taxonomy year is its own namespace, so us-gaap 2021–2026 is ~103k rows), excluding `xbrli:item`/`xbrli:tuple`; `source_schema_uri` is where it was first read, `is_extension` is whether the schema is in the filing itself. `xbrl_facts` keeps every occurrence (no dedupe), `fact_order` is document order then DOM order. Arelle has no `ixt-sec` (SEC 2015-08-31) registry, so facts in that format keep `raw_value` with null `normalized_value`/`numeric_value` (counted in `normalization_warnings`: 5,463/133,384 facts in `data/`). Fractions are stored as `"num/den"`; `xml_language` only for non-numeric facts. `block_id`/`cell_id` are set only when certain (cell first; hidden facts, facts spanning several blocks, XPaths matching several blocks stay null) and are not part of `fact_sha256`. `instances_recovered` = instances whose extension concepts are stored but no fact uses them yet (trace of a concepts commit whose facts failed).
- XBRL enrichment: `xbrl_dimensions` has one row per `xbrldi:explicitMember`/`typedMember` declared in a context's segment/scenario; taxonomy default dimensions are not materialized. Keyed by `context_key` (no `context_id`); `dimension_id` = `{context_key}:dimension:{NNNN}` in order (segment before scenario, then dimension QName). `typed_member_xml` uses XBRL core's `canonical_xml` (prefixes `ns0…`, like `segment_xml`), so it is prefix-independent; `typed_member_value` is normalized text. `xbrl_fact_footnotes` has one row per effective fact-footnote relationship Arelle resolves; a footnote on several facts shares one `footnote_resource_id` (hash of document + XPath). `footnote_text` is normalized text, `footnote_html` the inner markup (null if text only), `language` lowercase. The stage checks the model's `context_hash` and `fact_sha256` against the parent tables; Arelle loads only contexts used by facts, so an unused context with dimensions is rejected (none in `data/`). The expected dimension count derives from stored `segment_xml`/`scenario_xml`; an instance with no footnote rows is complete when its source document has no `ix:relationship`/`ix:footnote`/`link:footnoteLink`. In `data/` every footnote uses standard roles/link roles, `en-US`, at most 1 footnote per fact.
- XBRL linkbases: only effective relationships (Arelle has removed prohibited/overridden arcs) of `link:labelLink`, `presentationLink`, `calculationLink`, `definitionLink`; the network type comes from the extended link and every arcrole is kept (including calculation 1.1 `https://xbrl.org/2023/arcrole/summation-item`). `xbrl_labels` is a shared dictionary like `xbrl_concepts`: one row per concept-label relationship, all roles and languages (`language` lowercase); `label_text` is only NFC + LF + trim, whitespace not collapsed. `source_document_id` is a `document_id` when the file belongs to the filing, a URL for standard taxonomies, so standard labels share IDs across filings (deduped within the first batch, skipped afterwards). Network = (instance, linkbase type, role), no empty networks; `role_definition` comes from the DTS `roleType` (not inferred from the URI). Relationships: `order_value`/`weight` are plain decimals (`1.000` → `1`, `-0` → `0`); attributes not applicable to an arc are null, except `is_closed` (all/notAll arcs) and `is_usable` (dimension-domain/domain-member), which take their effective XDT value. `relationship_id` = `{network_id}:relationship:{relationship_hash}`. An instance is skipped when all its networks have their relationships (count, ordinals, `network_hash`); an instance with no networks is reloaded every run (none in `data/`). In `data/` every label is `en-US` and every endpoint is in `xbrl_concepts`.
- Joint filings (e.g. Exelon 0001109357 + Constellation 0001868275, four 8-Ks in 2022) are downloaded once per CIK, so one accession sits in two Bronze folders. The filings stage keeps one folder when all copies are identical (checksum): prefer the CIK that prefixes the accession (filer agent), else the smallest CIK (`duplicate_folders`, warning `sec_filing_duplicate_folders`); differing copies still reject. Folders the manifest records only as `status="failed"` (e.g. empty `full-submission.txt`) are skipped (`download_failed`, warning `sec_filing_download_failed`). The filings stage takes a file's SHA-256 from the manifest when every successful entry of the filing records one hash for that path and the file still has `size_bytes`; otherwise it hashes the file (`_recorded_sha256` in `transforms/sec_filings/filings.py`). Bronze is never overwritten; the documents stage reads the whole submission and rejects bytes that do not match the hash; the primary document is rehashed only by the audit (`--verify-source-hashes`, sampled filings). Before this, on 500-company Bronze, hashing all ~226 GB in the filings stage took ~2.7 h on exFAT.
- Newer SEC headers have fields `filing_entities` has no column for: `LEGAL ENTITY IDENTIFIER` (COMPANY DATA, 22 filings in 500-company Bronze) and `ADDRESS IS A NON US LOCATION` (address, 57 filings). The parser ignores these two keys (still readable from Bronze via the block offsets); any other unknown key rejects. The `CONFIRMING COPY:` flag (a line with no value before the first block) is a submission field, not an entity role.
- XBRL core: a source document that is not well-formed XML is skipped with warning `xbrl_source_not_well_formed` (broken HTML drops every Inline document of the filing, leaving the XML instance alone; with no source left the filing has no instance) instead of rejecting. In 500-company Bronze only Allegion 10-K `0001579241-25-000008`: SEC stored every document of that filing with a hard line break every 65,536 bytes, once inside an attribute name (`<td s⏎tyle`) and once inside an entity of the EDGAR-generated XML, so it has no XBRL (text/tables remain). `namespace_map` keeps each prefix's first binding in document order (Colgate `0000930413-21-001845` redeclares the default namespace on `ix:resources`).
- `xbrl_concepts` is keyed by expanded QName, but a filer can reuse an extension namespace across filings with slightly different declarations (Fifth Third 8-K `0000035527-26-000136`/`-000172`, Ford 8-K `0000037996-22-000015`/`-000017`: `domainItemType` of two DTR versions). For extension concepts the first definition wins and warning `xbrl_extension_concept_redefined` is logged; a differing standard-taxonomy concept still rejects.
- `primary-document.html` is not reproducible across downloads: SEC's edge appends a `<script>` tag with a random path (e.g. `/NgtUJUOBPgRU…`), so two downloads of one filing differ by a few bytes. Silver parses the `<TEXT>` slice of `full-submission.txt` (identical across downloads), so only `filings.primary_document_sha256` differs: comparing local `data/` with the homepc 500-company Silver (2026-11-03) on their 343 shared filings, every row of the other 18 tables is identical.
- `public_document_count` (header `PUBLIC DOCUMENT COUNT`) is unreliable: filings from 2024-01-30 to 2026-03-13 declare 1–2 more than the real `<DOCUMENT>` blocks (149/343 filings). The documents stage only logs `submission_document_count_mismatch`.

## Do not touch

- `data/` (gitignored; ~1.7 GB, 343 filings): do not edit or delete by hand.
  - `filing_manifest.jsonl` is append-only. Deleting a filing's files makes the next run download them again.
  - `_metadata/runs/run_*.json` is incremental state. One corrupt file makes every later run fail with `Invalid SEC run metadata`.
  - `_cache/arelle`: Arelle's taxonomy cache (not Silver), filled by builds with `--allow-taxonomy-network`. Deleting it means instances without facts cannot load offline (XBRL facts rejects with `xbrl_taxonomy_cache_miss` + URI) until redownloaded; complete instances still skip.
  - `_catalog/silver.db` (SQLite catalog) and `silver/` are managed by PyIceberg: never edit metadata or Parquet by hand. The catalog stores absolute paths, so moving `data/` breaks it.
  - Tests and trial runs use `tmp_path` or a temporary `--data-dir`.
- `.env`: holds a real name and email sent to SEC in the User-Agent. Never print or commit it.
- `uv.lock`: change only through `uv add` / `uv lock`.
- `infrastructure/gcp_vm/.terraform.lock.hcl`: generated by `terraform init`.
- `src/data_pipeline/erd/conceptual_erd/*.{png,svg,html}`: exported from `conceptual_erd.drawio`; edit the `.drawio` and re-export. [?] Purpose of `Untitled Diagram.drawio` unknown. [?]
- `logs/lexifin.jsonl`: JSON logs of earlier runs. Code only writes to stdout, so this was likely a redirect. [?]

## Known traps

Dangerous or costly to run:

- Ingest calls real SEC EDGAR and iShares and uses disk: 5 companies × 5 years ≈ 1.7 GB, ~8 min (from `logs/`). 500 companies ≈ 170 GB, more than the Terraform VM's 50 GB disk. [?] Always try N=1, 1 year, and a temporary `--data-dir`.
- `sec-edgar-downloader` calls `requests.get` without a timeout and can hang forever (seen 2026-10-04: stuck in SYN-SENT over IPv6 to sec.gov). Set an external timeout.
- Never run two ingest processes on one `--data-dir`: no lock, both append to the manifest. The 10 req/s SEC rate limiter is per process; exceeding it may get the IP blocked. [?]
- `build_silver.py --allow-taxonomy-network` sends the `.env` User-Agent to xbrl.fasb.org, xbrl.sec.gov, www.xbrl.org… to fetch missing taxonomies (cached files are not refetched). Each download has a 60 s timeout (`internetTimeout`; an HTTP connection to Cloudflare once hung forever); a failed download counts as missing and the stage rejects. Online, Arelle tries `http://www.w3.org/2001/xml.xsd` for every instance and gets 403; the instance still loads but slower (~7 s vs median 1.6 s offline). Offline by default; tests never enable network.
- The dev machine has 15 GB RAM: full build ~2.6 GB (Arelle DTS), rerun ~0.75 GB, audit ~0.7 GB. Ad-hoc analysis of `data/` must read only needed columns, run under a hard RAM cap (e.g. `systemd-run --user --scope -p MemoryMax=5G -p MemorySwapMax=0 …`, killed instead of freezing the machine) and never alongside the test suite or a build. On 2026-10-07 a script loading every column of all 19 tables into DuckDB (default up to 80% of RAM) alongside the test suite froze the machine twice.
- PyIceberg 0.12 `scan().to_arrow_batch_reader()` has no memory bound: it reads all files of the scan in parallel and holds each file's batches until consumed. Reading Parquet with multithreaded pyarrow (the `iter_batches` default) makes mimalloc keep every thread's freed memory, so RSS grows with file count even though Arrow's pool holds a few MB (measured on `xbrl_facts`: ~700 MB). All Silver reads go through `scan_batches` (`storage/iceberg.py`): one file at a time, `use_threads=False`, then `release_unused()` (~180 MB); never call `scan().to_arrow()` on a whole table.
- `terraform apply` in `infrastructure/gcp_vm/` creates an `e2-standard-4` VM with a 50 GB disk in `asia-southeast1`, billed until destroyed. Never run `apply`/`destroy` unless asked. tfstate is gitignored, so state lives only on the machine that ran it. [?]
- `my_ip` defaults to `0.0.0.0/0`: the firewall opens ports 22, 6333, 7474, 7687, 8501 to the whole Internet.
- `docker-compose.yml` hardcodes the Neo4j password and uses image `qdrant:latest`. Data goes to `qdrant_data/`, `neo4j_data/` next to the compose file; they are not gitignored, so `git add -A` adds database files.
