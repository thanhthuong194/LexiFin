# Gold: native RAG chunks (`native_rag.chunks`)

One Iceberg table of retrieval chunks built from the Silver narrative by `scripts/native_rag/build_chunks.py`. Source of truth is the code: schema and row checks in `contracts/native_rag/chunks.py`, table spec in `storage/native_rag/chunks.py`, chunking rules in `transforms/native_rag/`, batching and metadata in `pipelines/native_rag/`, audit in `quality/native_rag/audit.py`. Design and decisions: `docs/plans/native_rag_chunking_draft.md`.

Numbers are from `data/` (343 filings, 523 narrative documents), 2026-11-16.

## 1. Storage

- Own catalog: `<gold_dir>/_catalog/gold.db` (PyIceberg `SqlCatalog`, SQLite), files under `<gold_dir>/gold/native_rag/chunks/`. `gold_dir` defaults to the Silver `--data-dir`. Purging Gold never touches the Silver catalog.
- Partition `year(filing_date)`. Grain: one chunk of one narrative document (primary HTML or EX-99 exhibit). Key `chunk_id` = `{document_id}:chunk:{NNNNNN}`.
- Table properties pin what rows were built with; a run whose values differ writes nothing (`rejected`): `lexifin.rules-version`, `lexifin.tokenizer` (`Qwen/Qwen3-Embedding-0.6B@<revision>`), `lexifin.chunk-params` (all tunables), `lexifin.silver-rules` (rules versions of every Silver table read: filings, documents, filing_entities, sections, content_blocks, document_tables, document_table_cells, exhibits, xbrl_instances, xbrl_contexts, xbrl_concepts, xbrl_facts). Change any of them: purge `native_rag.chunks` with `open_gold_catalog`, then build.

## 2. Columns

| Use | Columns |
|---|---|
| Keys, links | `chunk_id`, `filing_id`, `document_id`, `section_id`, `table_id` (table chunks), `block_ids` (Silver blocks whose text the chunk holds, in order) |
| Filter | `cik`, `tickers`, `form`, `fiscal_year`, `fiscal_period` (FY/Q1–Q3; null for 8-K), `period_end_date`, `filing_date`, `section_topic`, `document_type`, `chunk_kind` (text/table) |
| Citation | `company_name`, `accession_number`, `sec_url`, `section_title`, `subheading`, `table_title` |
| Context expansion | `chunk_ordinal` (document order), `document_chunk_count`, `part`/`part_count` (pieces of one paragraph or one table) |
| Content | `context` (prefix), `text` (body) |
| Control | `token_count`, `chunk_sha256`, `processed_at` |

- Embedded string = `context + "\n\n" + text`; `token_count` counts it with the Qwen3-Embedding tokenizer including `<|endoftext|>`; `chunk_sha256` hashes it. Cap 512 tokens.
- `context`: `Company | form | period | section path › subheading[ | Table: title (part i/n)]`. Period: `FY2025 (period ended …)`, `FY2025 Q2 (…)`, 8-K `filed … (event …)`.
- `company_name`: dei `EntityRegistrantName` of non-dimensional contexts (a multi-registrant filing names each subsidiary under `LegalEntityAxis`), one spelling per CIK when names differ only in case/punctuation/suffix: the earliest filing's, mixed case first, so new filings never change it; fallback the filer's conformed name. `tickers`: dei `TradingSymbol` of contexts whose `Security12bTitle` is not debt, `^[A-Z][A-Z.\-]{0,9}$`. `period_end_date`, fiscal fields: dei of non-dimensional contexts, fallback `report_date`.
- `section_topic`: `cover`, `business`, `risk_factors`, `cybersecurity`, `properties`, `legal_proceedings`, `market_equity`, `mdna`, `market_risk`, `financial_statements`, `controls`, `governance`, `exhibits`, `signatures`, `8k_event`, `ex99`, `other`; 10-Q items keyed by parent PART. Known mislabel: financial pages filed under 10-K ITEM 15 are `exhibits`.
- `section_title`: last element of the path; primary-document root = `Cover page`, prose kept from a TOC section = `Front matter`, EX-99 root = `EX-99.1: {Exhibit Index description}`.

## 3. Chunking rules

Structure-aware, deterministic, no LLM. Per document: drop noise → read tables → per run of blocks of one section: text between tables in topic units, each data table its own chunk.

- Noise (counted in `dropped_blocks`): lines ≤150 chars in a TOC section, or only TOC-shaped lines (PART/ITEM start, page-number end) when the section has over 100 such lines (not a real TOC: Silver found no item heading, e.g. Entergy 10-Qs); tables there are classified like any other; the block opening a detected section when it is at most min(title, 200) + 40 chars (the title goes to the path; an 8-K item laid out as one table stays); empty; no letters/digits; page numbers (`12`, `Page 3`, `xii`, `F-12`, `23.`); running headers (≤100 chars, not a sentence, same text with digits as `#` ≥4 times in ≥3 sections or ≥8 times, and either `Table of Contents`, a rising page counter, or at least half its occurrences within 3 blocks of a page break: row labels of tables laid out as text stay); TOC-like tables (no `$`, most rows start with PART/ITEM or are a label of 20+ chars and a page number) and signature tables anywhere.
- Tables: TOC/signature → dropped; ≤2 non-empty columns or no numeric cell → paragraphs (one per row); data table with block text <100 chars → one inline paragraph; otherwise rendered from cells as `label | value | value` with an inferred header (years/dates are labels), `$`/`%`/`)` glued to numbers (lowercase `x`/`bps` only right after a value; uppercase `X` is a check mark), units rows as notes; title = last short paragraph or a lead-in ending in `:` plus up to 3 title-like lines above; up to 5 following footnotes, then short lines that close the table (statement footers such as "See accompanying Notes…" and short notes; together under 64 tokens, not title-like or lead-ins, followed by a table, a heading, a `:` lead-in or the section end; right before a table only a statement footer, since another line introduces that table; rules v5); split by rows with the header repeated (a row over the cap is cut by tokens; parts are checked against their real `(part i/n)` prefix). Known weakness: a very wide table (15 columns, ~400-token header) gives one row per part, mostly header.
- Word-fragmented documents (over 300 text blocks, more than half ≤15 chars: absolutely positioned layouts, 55 on 500-company Silver) have consecutive text blocks joined into paragraphs ending at `.`/`!`/`?`/`:`, without subheadings.
- Text: a title-like line (≤120 chars, ≤12 words, no final `.,;:` except a company suffix) opens a unit; unit ≤ cap → one chunk; longer → fewest balanced parts between paragraphs; a paragraph over the cap → balanced parts of sentences (a sentence over a third of the budget cut by tokens), each repeating the previous part's last piece when it is at most a quarter of the budget (rules version 2: v1 let 5 documents of the 500-company Silver reach 513–514 tokens); unit <64 tokens merges into the next unit, else the previous, when it fits; never across sections or tables.

## 4. Operation

- Incremental by document: complete documents (ordinals 1..N = declared count) are skipped; documents with no chunks (image-only exhibits) are re-examined each run; an incomplete stored document rejects the run. Batches by filing date of at most 200 documents or 300k cells, one verified commit each. A document whose chunks fail (contract, cap) is skipped and logged; the run ends `partial` (exit 1) and retries it next time. A layout table's rows may continue in the next chunk; every other block is in exactly one chunk or a split chain.
- Audit (`--check-only`, or after every build): definition and properties, contract on every row, keys, ordinals, token cap, hashes, FKs (document, section, each block in Silver and in the chunk's section), each non-table block in one chunk outside split chains, documents without chunks and >30% of characters outside chunks (WARN), exact rebuild of the newest 10-K/10-Q/8-K plus 5 documents by hash with full coverage (every block in a chunk or dropped, not both). Reads one filing year at a time.
- `data/` (2026-11-16): build 80 s, peak RSS ~0.7 GB, rerun 0.8 s; 26,024 chunks, tokens mean 287, max 512; audit PASS (16 checks).

## 5. `native_rag.embeddings`

One vector per (model, chunk), built by `scripts/native_rag/build_embeddings.py` through `src/llm` (`get_embedder(<profile>)`, profiles in `config/llm_profiles.toml`; the default profile is Qwen3-Embedding-0.6B served by vLLM, URL and key in `.env`). Code: contract `contracts/native_rag/embeddings.py`, spec `storage/native_rag/embeddings.py`, pipeline and audit `src/rag_engine/embedding/`.

- Same Gold catalog as chunks, partition `year(filing_date)`. Key `embedding_id` = `{model_id}|{chunk_id}`; columns `chunk_id`, `document_id`, `filing_date`, `model_id`, `chunk_sha256` (hash of the embedded text the vector was made from), `dimensions`, `vector` (float32, L2-normalized: cosine = dot product), `processed_at`. Several models can share the table.
- Embedded string = the chunk's `context + "\n\n" + text` (the string the chunker counted); documents get no instruction, queries get the profile's `query_instruction`.
- Incremental: chunks whose (`chunk_id`, `chunk_sha256`) already has a vector of the model are skipped; vectors are written in verified commits of 4,096 rows, and vectors made before a failed request are committed, so a closed Colab tunnel only stops the run: it ends with status `interrupted` (exit 1, vectors made so far committed, rows never appended twice); put the new URL in `.env` and run again. Vectors whose chunk is gone or changed (chunks rebuilt, years of either table checked) or of another size reject the run before any request: purge `native_rag.embeddings` and embed again.
- `--concurrency N` request groups of 128 chunks in flight (the server batches them); `--limit N` for trial runs.
- Audit (after every run, or `--check-only`; one pass over each year's vectors): definition, unique keys, one vector size and every vector that long, norms within 1e-3 (NaN fails), every vector's chunk current (FAIL), chunks without a vector (WARN), `--reembed-sample` current chunks re-embedded with cosine >= 0.999 (WARN when the server is down). Between sessions of a long run, `--skip-audit` saves the full vector read.
- `data/` (2026-11-17, Qwen3-Embedding-0.6B on a Colab T4 through a Cloudflare tunnel): 26,750 vectors (rules v4 chunks) in 22.7 min (19.6 chunks/s; concurrency 4 and 8 give the same rate, the GPU is the limit), peak RSS 0.84 GB, ~112 MB on disk; audit PASS (8 checks). At that rate the 500-company chunks (~3.7 M) take ~57 h.

## 6. Qdrant (`scripts/native_rag/load_qdrant.py`)

Serving index rebuilt from Gold at any time (`native_rag.chunks` + `native_rag.embeddings`); code in `src/rag_engine/indexing/`.

- One collection per (corpus, chunks rules version, index version, model): `sec_filings__chunks_v4__index_v1__qwen_qwen3_embedding_0_6b`; `INDEX_VERSION` (in `qdrant_store.py`) covers the payload fields and the BM25 vector, which chunk hashes do not, so bump it when either changes. Later corpora (`vn_filings`, `us_law`, `vn_law`) get their own. The application reads the corpus alias (`sec_filings`), switched only after a load whose audit has no FAIL and whose HNSW is built (`--check-only` never switches it).
- Point ID = UUID5 of `chunk_id`. Vectors: `dense` (1024, cosine) and `bm25` (sparse: BM25 term-frequency weights of `context + "\n\n" + text`, lowercase words and numbers, English stopwords dropped, CRC32 term IDs, average length 116 terms measured on local Gold; Qdrant applies IDF). Hybrid queries fuse both with RRF; the query side uses `sparse.query_vector`.
- Payload: `chunk_id`, `filing_id`, `document_id`, `section_id`, `cik`, `tickers`, `company_name`, `form`, `document_type`, `fiscal_year`, `fiscal_period`, `filing_date`, `period_end_date` (RFC 3339), `section_topic`, `section_title`, `subheading`, `chunk_kind`, `table_title`, `chunk_ordinal`, `part`, `part_count`, `accession_number`, `sec_url`, `context`, `text`, `token_count`, `chunk_sha256`, `corpus`, `jurisdiction`, `language`. Indexes: `cik` keyword with `is_tenant`; keyword `tickers`, `form`, `document_type`, `section_topic`, `chunk_kind`, `fiscal_period`, `filing_id`, `document_id`, `section_id`, `corpus`; integer `fiscal_year`, `chunk_ordinal`; datetime `filing_date`, `period_end_date`.
- Parameters: HNSW m 16, ef_construct 200, search `hnsw_ef` 128. `--large` (500 companies): int8 scalar quantization (quantile 0.99, in RAM) with rescoring and oversampling 2.0, original vectors, sparse index and payload on disk. A new collection is filled with indexing off, then `indexing_threshold` 20000. An existing collection must have exactly the requested layout, else the run stops (delete it and load again). Over 500,000 chunks the load refuses to run without `--large`.
- Incremental, one filing year at a time and inside it one chunk data file at a time (Gold files are commit batches spanning many months, so month filters would reread a year 12 times): points are compared by `chunk_sha256` without reading vectors; only new or changed chunks have their vectors read (Arrow float32, by `chunk_id` file pruning) and are upserted (512 per acknowledged request; 5xx, 429 and connection errors retried with backoff, 4xx not); points no current Gold chunk backs, or of years Gold no longer has, are deleted. Chunks without a current vector leave the run `incomplete` (exit 1; embed, then load again).
- Audit (after the index build, or `--check-only`): collection, point count = Gold chunks with a current vector, payload indexes, sampled points equal Gold (payload, dense cosine >= 0.999, BM25 indices and weights), self-retrieval, hybrid query filtered by `cik` returns the chunk and only that company, HNSW vs exact top-10 recall (mean >= 0.95, each >= 0.7; SKIP before HNSW covers 90% of vectors or on embedded Qdrant). Tests use embedded Qdrant (`QdrantClient(":memory:")`); runs use the server (`--qdrant-url`, default `http://localhost:6333`) or `--qdrant-path`.
- `data/` (2026-11-17, local Docker Qdrant 1.20.0): load 34 s, 58 s with the index build and audit, peak RSS 0.75 GB; rerun 2.9 s; audit PASS (7 checks, ANN recall 1.000).
